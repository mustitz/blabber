# Ізоморфізм Карі Говарда

Світ трохи погудів навколо вирішення проблеми Нав'є-Стокса.
Вийшло багато відео, які пояснюють для домогосподарок яка проблема вирішувалася.
Я не експерт у PDE, тому мені важко оцінити, наскільки ці відео чесні: де вони спрощують на межі підміни понять, а де просто мовчать про незручні деталі
Я програміст, тому я більше звернув увагу на Lean 4, адже доказ це програма на цій мові програмування.
Передбачу, що багато розробників тут скаже про себе: «Що за маячня!»
Так, я тут трохи в темі, тому й вирішив пояснити на пальцях як таке може бути.

Ізоморфізм Карі Говарда це твердження про те, що можна поставити відповідність між математичними твердженнями та деклараціями функцій у мові програмування,
та між доказами та реалізацією функцій.
Звучить дивно, спробую пояснити на прикладі.
Подивимося на функцію на Go

```go
func modusPonens(a A, f func(A) B) B
```

ми можемо досить легко придумати, як її реалізувати таким чином, щоб задовільнити компілятор

```go
func modusPonens(a A, f func(A) B) B {
    return f(a)
}
```

Але припустимо у нас є інша функція:
```go
func nonsense(a A, f func(B) A) B
```

Як можна реалізувати її?
Так, в більшості мов програмування у нас є багато трюків для цього.
Наприклад, можна повернути `null`, можна якось створити об'єкт, можна зафорсити приведення типів
Але, якщо заборонити всі ці трюки, то досить легко переконатися, що написати тіло функції не можна.

Чому?
Перша функція це закодована логічна формула: `(A ∧ (A → B)) → B`
Ця формула має навіть власну назву, це modus ponens, з латини приблизно «спосіб, що стверджує»
Цей сіллогізм відомий ще з античності, хоча латинська назва з'явилася значно пізнише.
Якщо A → B цеімплікація, то ми можемо побудувати таблицю істиності

| A | B | A → B | A ∧ (A → B) | (A ∧ (A → B)) → B |
|---|---|--------|--------------|----------------------|
| 𝔣 | 𝔣 | 𝔱      | 𝔣            | 𝔱                    |
| 𝔣 | 𝔱 | 𝔱      | 𝔣            | 𝔱                    |
| 𝔱 | 𝔣 | 𝔣      | 𝔣            | 𝔱                    |
| 𝔱 | 𝔱 | 𝔱      | 𝔱            | 𝔱                    |

Ми бачимо, що функція незалежно від значень A та B на виході дає 𝔱
Такі висловлювання називаються тавтологіями

У математиці такі завжди-істинні формули якраз і називають теоремами.
Тобто теорема, це не просто красиве твердження, а те, що можна довести, спираючись на аксіоми та правила виводу.

Якщо подивитися на функцію `nonsense` то бачимо  (A ∧ (B → A)) → B

| A | B | B → A | A ∧ (B → A) | (A ∧ (B → A)) → B |
|---|---|--------|--------------|----------------------|
| 𝔣 | 𝔣 | 𝔱      | 𝔣            | 𝔱                    |
| 𝔣 | 𝔱 | 𝔣      | 𝔣            | 𝔱                    |
| 𝔱 | 𝔣 | 𝔱      | 𝔱            | 𝔣                    |
| 𝔱 | 𝔱 | 𝔱      | 𝔱            | 𝔱                    |

Бачимо, що при A = 𝔱, B = 𝔣 формула хибна.
Отже, це не тавтологія, а значить не теорема, і тому тіло функції `nonsense` написати неможливо (без трюків).

Тут все можна бачити начатки ідеї: якщо можна написати тіло функції, то висловлювання, яке вона кодує, істинне.

## Мови програмування за залежними типами

Відразу виникає питання, чи можна придумати таку мову програмування, щоб вона була в якомусь сенсі евківалентна математиці?
Вочевидь, C, Java, Go та інші подібні мови дуже сильно впираються у виразність: вже на простому `¬` для довільного висловлювання виникають проблеми.
Тому вони просто не годяться.
Так, я думаю що більшість здогадалися, що такою мовою програмування є Lean 4.
Але все-таки не все так просто.

По-перше, мова програмування не має містити трюків, які дозволяють написати тіло будь якої функції.
З'ясувалося, підходять чисто функціональні типизовані мови програмування, тобто без змінних.
Далі, ще одна умова це тотальність функції.
Це визначеність, компілятор має перевірити, що в коді немає виключень, всі ситуації оброблені,
та кінцевість, тобто компілятор має перевірити, що функція колись завершеться.

І тут вже цікаво.
Багато хто чув про те, що проблема зупинки машини Т'юрінга нерозв'язна.
Тобто компілятор має перевірити нерозв'язну проблему?
Як таке може бути?

Відповідь проста: мова не має бути Т'юрінг повною.
Як так? Якийсь brain fuck це Т'юрінг повна мова, а тут..?
Фокус в тому, що можна ослабити мову програмування таким чином, щоб вона не була Т'юрінг повною,
але щоб на ній можна було вирішити багато практичних задач.
Цей фокус називається структурна рекурсія.
Про неї поговоримо пізніше.

По-третє, це залежні типи
Знову концепція, яку не часто зустрінеш у ширвжиткових мовах.
Знову треба пояснити пізніше.

## Структурна рекурсія

Спробуємо пояснити на пальцях.
Всі чисті мови програмування не мають змінних.
Тобто значення створюється один раз назавжди.
Наприклад, список може конструюватися двома шляхами: або робимо пустий, або створюємо з елементу та хвоста.
При цьому компілятор має слідкувати, щоб в нас не було нескінченних структур на кшталт `ones = 1 : ones` в лінивому Haskell.
Далі просто, компілятор перевіряє рекурсивні виклики, та намагається знайти аргумент,
де ми передаємо частинку від значення, яке прийшло у функцію.
Трохи заплутано, але давайте подивимося:

```python
def mylen(lst):
  if lst == []:
      return 0
  head, *tail = lst
  return 1 + mylen(tail)
```

В цьому коді видно, що рекурсивний виклик `mylen` буде над частиною lst,
він буде постійно зменшуватися, а значить нескінченної рекурсії ніколи не може бути.
А от якщо написати

```python
def find(lst, value, i):
    if i >= len(lst):
        return None
    if lst[i] == value:
        return i
    return find(lst, value, i+1)
```

то хоча й метод гарантовано закінчить свою роботу, компілятор перевірити це не в змозі.
Тут `lst` передається без змін, структурно перші два аргументи не зменшується, а третій навіть збільшується.
Рецепт? Переписати алгоритм так, що компілятор побачив:

```python
def find_proved(lst, value, i):
    if not lst:
        return None
    head, *tail = lst
    if head == value:
        return i
    return find_proved(tail, value, i+1)
```

Окреме питання що робити, коли термінація не дуже очевидна. Як-то бінарний пошук.
Ну... тоді треба або додати такий аргумент, або тицьнути компілятор носом в такий аргумент, та писати доказ що це дійсно так.
Наприклад, бінарний пошук на Lean може виглядати приблизно так:


```lean
def find (lst : Array Int) (v : Int) (l r : Nat) (hr : r ≤ lst.size) : Option Nat :=
  if h : l < r then
    let m := (l + r) / 2
    have hm : m < lst.size := by omega
    if lst[m] = v then some m
    else if lst[m] < v then find lst v (m + 1) r hr
    else find lst v l m (by omega)
  else
    none
termination_by r - l
decreasing_by
  · omega
  · omega
```

Думаю, якщо напрягтися, то можна побачити код бінарного пошуку.
Так, ML-нотація, знайома хаскелістам та іншим функціональщикам, де аргументи функції пишуться через прогалину, для інших незвична.
Замість звичного `find(lst, v, l, m, by omega)` ми бачимо `find lst v l m (by omega)`.
Але якщо до цього звикнути, то це майже один в один наступний код

```python
def find(lst, v, l, r, _):
  if l < r:
    m = (l + r) // 2
    if lst[m] == v:
      return m
    elif lst[m] < v:
      return find(lst, v, m+1, r, _)
    else:
      return find(lst, v, l, m, _)
```

Що відрізняє код на Lean?
По-перше, імена типів.
`Array Int` це масив цілих чисел, `Int` ціле, `Nat` це натуральне число,
причому нуль це натуральне, а не так як мене вчили у школі.
Цікаве останнє: `hr : r ≤ lst.size`.
Функція вимагає останнім аргументом доказ того, що r не більше кількості елементів у масиві.

Коли ми зайдемо у функцію, то в нас додатково буде доступний доведений факт `hr`.
На жаль в Python так зробити не можна, тому прочерк.
Функція повертає `Option Nat`, натуральне число або `none`, маркер відсутності результату,
вже знайомий для багатьох тип запозичений з чистого функціонального програмування.

Тепер читаємо функцію.
Порівняно з Python в `if` з'явився префікс `h :` перед умовою.
Це, як й `hr`, ім'я факту.
Оскільки ми перевірили умову, то в гілці if/true вона стає доведеним фактом `h`, який можливо ми захочемо потім використати.

Далі `let` дає ім'я значенню.

Далі `have`. Це аналог `assert`...
Я стверджую, що значення `m` має бути строго менше за довжину масиву.
Після `:=` має йти доказ.
`by omega` означає що мені його ліньки писати, тому я прошу омегу знайти його для мене.
omega це солвер, який шукає докази тривіальних (й не дуже) арифметичних висловлювань.
Мене це влаштовує.

Далі звичайнісінький алгоритмічний код, от тільки в рекурсивному виклику нам треба вставити докази факту.
В першому разі доказ у нас вже є, це `hr`, бо нічого не змінилося.
В другому `by omega`, теж прохання до солвера виконати за нас нашу роботу.

Далі... памʼятаєте, я казав, що треба аргумент, який зменшується?
Ось він, тільки записаний окремо: `termination_by r - l`.
Лічильник не тягнеться через усі виклики й не засмічує сигнатуру,
ми явно висказали наші наміри назвавши величину, яка спадає.

Але назвати мало, компілятор на слово не вірить, йому треба доказ, що вона справді спадає.
Рекурсивних викликів два, тому й доказів два.

![vim з відкритим Lean](binary-search.png)

На цьому скріншоті показаний vim де можна побачити типовий робочий сценарій у Lean.
Курсор знаходиться на ідентифікаторі `decreasing_by`, LSP показує нам, які докази треба зараз написати.
Це дві цілі для кожного рекурсивного виклику.
Також виведено багато фактів, які в цей момент відомі компілятору,
серед яких можна знайти аргумент `hr`, та два факти `h` та `hm` які ми додали й довели самостійно.

Все, готовий бінарний пошук, де ми довели відсутність виходу за межі масиву та той факт, що немає зациклювання.

## Залежні типи

Настав час перейти до іншої унікальної особливості мов програмування зі залежними типами,
ністільки унікльної, що вона винесена навіть в назву.
Структурна рекурсія це обмеження доказів, якщо її відмінити, то можна буде легко доказати
будь який вислів, що `2+2=5`, що `True=False` тощо.
А от саме залежні типи додають до мови виразність, яка дозволяє сформулювати будь-яке математичне висловлювання.
Що це таке?

Залежний тип це властивість мови, коли у функції типи наступних аргументів можуть залежати від попередніх.
І в мейнстрімних мовах дуже важко навіть знайти аналоги.
Чимость це нагадує шаблони в C++, наприклад

```cpp
template<typename T>
T iif(bool cond, T value1, T value2)
{
    return cond ? value1 : value2;
}
```

Тут фактично функція `iif` приймає 4 параметри: тип `T`, умову `cond`, та значення `value1` та `value2`.
Залежні типи це трохи ширша концепція, бо в C++ шаблонний параметр живе виключно під час компіляції,
що часто трапляється, але необов'язково у мовах програмування зі залежними типами.
Так, можна написати функцію `printf` з виводом типів параметрів під час компіляції, тобто

```c
    printf("Value: %d", 42);
```

буде компілюватися, а

```c
    printf("My answer: %s", 42);
```

впаде з помилкою компіляції. Це те, що сучасні C/C++ роблять виключно для вбудованих форматування.
Спробуйте додати власну функцію з трохи розширеними можливостям на кшталт `"Today %{date}"` й компілятор нічим не допоможе.
А ось приклад такої функції з туторіала Idris:

```idris
printf : (fmt : String) -> FormatType (parseFormat fmt)
```

`fmt` це є наш рядок з форматом.
`parseFormat` це функція, яка поверне розпаршений формат як список.
Вона може виглядати так:

```idris
data Format = FInt Format | FString Format | FLit Char Format | FEnd

parseFormat : String -> Format
parseFormat ('%' :: 'd' :: cs) = FInt (parseFormat cs)
parseFormat ('%' :: 's' :: cs) = FString (parseFormat cs)
parseFormat (c :: cs)          = FLit c (parseFormat cs)
parseFormat []                 = FEnd
```

Визначення типу Format тут рекурсивне, для рядку "%s=%d" вона поверне
`FString(FLit '=' FInt(FEnd))`

А головна магія це `FormatType`, який перетворює цю послідовність на справжній тип мови:

```idris
FormatType : Format -> Type
FormatType (FInt fmt)    = Int -> FormatType fmt
FormatType (FString fmt) = String -> FormatType fmt
FormatType (FLit _ fmt)  = FormatType fmt
FormatType FEnd          = String
```

Для нашого прикладу отримаємо такий ланцюжок перетворень:

```
FormatType (FString(FLit '=' FInt(FEnd)))
String -> FormatType (FLit '=' FInt(FEnd))
String -> FormatType (FInt(FEnd))
String -> Int -> FormatType(FEnd)
String -> Int -> String
```

Таким чином тип виразу `printf "%s=%d"` це `String -> Int -> String`,
тобто це функція, яка приймає `String` та `Int` та повертає `String`.

Це все добре, це круто, але як це пов'язано з математикою?
Повернемося до нашого прикладу на Lean:

```lean
def find (lst : Array Int) (v : Int) (l r : Nat) (hr : r ≤ lst.size) : Option Nat :=
```

Наші аргументи тут `lst`, `v`, `l`, `r`, `hr`.
Зверніть увагу на останній аргумент `hr`, та його тип `r ≤ lst.size`.
Трохи дивно бачити замість типу мати умовний вираз.
Тут `≤` це не булеве значення, а конструктор типу, який приймає два числа й повертає тип доказів, що перше не більше другого.
В Lean він визначений приблизно так:

```lean
inductive Le : Nat → Nat → Prop
  | refl (n : Nat) : Le n n
  | step (n m : Nat) : Le n m → Le n (m + 1)
```

Тобто довести `Le n m` означає побудувати значення цього типу: або `refl n`, коли `n = m`,
або `step`, накручуючи +1 до правої межі стільки разів, скільки треба, щоб можна було застосувати `refl`.
Так `2 ≤ 4` це тип, значенням якого може бути `step 2 3 (step 2 2 (refl 2))`: `refl 2` дає `2 ≤ 2`, перший `step` піднімає до `2 ≤ 3`, другий до `2 ≤ 4`.
А `4 ≤ 2` це також тип, жодного значення якого ми побудувати не можемо,
таким чином типи й стають висловлюваннями, а хибні висловлювання це такі типи, які не мають значень.

Повернемося до визначення `find`.
Ми бачимо, попередні аргументи `r` та `lst` як раз й використовуються для того, щоб скоструювати тип для факту,
який обмежує `r`.

Якщо у функціональних мовах програмування функції є громадянами першого класу,
які не відрізняються від таких інших значень, як цілі, рядки, тощо,
то у мовах програмування зі залежними типами, типи також потрапляють в перший клас.

Я не планував у це сильно в це занурюватися, концепція складна настільки, що треба повністю її освітити треба окрема стаття.
Це лише нарис головної ідеї, яка, повторюся, дає мові достатньо виразності для того щоб написати будь яке математичне висловлювання.

## Різні математики

Ок, добре, припустимо що ми зробили таку мову програмування.
Чи буде вона еквівалентна математиці?
Тут починається багато цікавого.
Питання перше, «а що таке математика?»
Або точніше, які системи аксіом лежать в основі?

Історично більшість математиків працювали у системі аксіом теорії множин, яка мала назву ZFC.
Довгий час це вважалося взагалі єдиною можливою системою.
Можливо тому, що фон Нейман спробував придумати іншу систему аксіом, відому як NBG (теорія множин фон Неймана, Бернайса та Ґьоделя)
Та згодом вияснилося, що його система аксіом еквівалентна ZFC.
Це налаштовувало на думку, що іншого вибору просто немає.

Але життя бентежне й цікаве, вибір є!
Дослідження по теорії категорії з'ясували, що не існує єдиної правильної категорії множин.
Категорія множин, яку задає ZFC, це лише один приклад ширшого класу структур, елементарних топосів,
де кожен такий топос з об'єктом натуральних чисел задає свою власну внутрішню логіку й самодостатню математику.
А якщо зрозумілою мовою, ZFC це можливий, але не єдиний вибір.
Мови програмування зі заледними типами дають альтернативні системи аксіом.
Так, я не обмовився, їх навіть не дві.

В залежності від лямбда-числення, яке лежить в основах мови, отримуємо різні системи аксіом.
Так Lean 4 та Rocq це мови на основі числення індуктивних конструкцій (Calculus of Inductive Constructions, CIC).
Agda це інтенсійна теорія типів Мартіна-Льофа (Martin-Löf Type Theory, MLTT).
Cubical Agda це те саме, але з кубічною теорією типів, яка дозволяє обчислювально працювати з univalence.
Є ще Idris, який відпочкувався в напрямку quantity, тобто квантитативної теорії типів (Quantitative Type Theory, QTT), що еквівалентно Agda,
але дозволяє чіткіше слідкувати за тим, що попаде в runtime, а що лишиться тільки на етапі компіляції.

Проте з точки зору більшості математиків різниці між цими аксиомами немає.
Більшість практичних математичних результатів можна довести в усіх цих системах аксіом.
Так, коли мова заходить про ордінали високих ступенів, то там виникають нюанси,
але це настільки езотеричний розділ,
це настільки не використовується в практичних задачах,
що про це можна спокійно забути, якщо ти не пишеш дисертацію з теорії доведення.

Цікаво, що перші спроби побудувати математику на базі залежних типів зазнали невдачі.
І проблема була у тому, що був введений тип всіх типів, до якого належав будь який тип, тобто `Type : Type`.
Щось на кшталт пайтонівського `Type`.
З'ясувалося, що теорія тоді стає беззмістовною, бо в ній можна довести будь який факт!
Тобто, програмувати ніхто не заважає, всі переваги лишаються, а от з ідеєю формалізації математики треба розпрощатися.
Ідея та сама, що й в парадоксі Рассела про множину всіх множин,
якщо вона існує, то можна побудувати множину всіх множин які не містять саму себе й запитати, а чи така множина містить сама себе?
Брадобрей бриє всіх хто не бреється сам.

Тому зараз всі мови програмування мають ієрархію типів з індексами: `Type₁ : Type₂ : Type₃ : ...`.
Кожен рівень належить наступному, а не самому собі, тому `Type : Type` побудувати вже не можна.
Це виключає цей хак, але... теорема Гьоделя, довести несуперечність у середині системи неможливо,
тому CIC та MLTT це ще й страхування, якщо одна з систем навернеться, то може це не зачепить інші?

## Інтуїціонізм та закон виключення третього

Я не торкався ще одного цікавого моменту.
Математика поділяється на класичну та інтуїціоністську.
Історія тягнеться ще за часів Гільберта, який серед інших формалізував математичні аксіоми логіки,
які залізобетонні, мають виконуватися завжди і скрізь.
Серед них була аксіома виключення третього, або A ∨ ¬A.
Дійсно, якщо побудувати таблицю істинності, то ця формула є тавтологією.

| A | ¬A | A ∨ ¬A |
|---|----|---------|
| 𝔣 | 𝔱  | 𝔱       |
| 𝔱 | 𝔣  | 𝔱       |

Але був математик Брауер, який вважав цю аксіому сумнівною.
В результаті виникла дуже цікава переписка, в якій Гільберт наводив яскраві приклади,
що заборонити математику користуватися законом виключення третього це як заборонити боксерам бити кулаками.
Так, дійсно, закон виключення третього, а за ним й доказ від зворотнього це потужні математичні техніки.
Але осад лишився.

**Теорема**: існують ірраціональні числа a, b, для яких a^b (a в степені b) раціональне.

**△**
  Вважаємо, що ірраціональність числа √2 довели ще давні греки.
  Візьмемо число c = √2^√2.

  * Якщо воно раціональне, то теорема доведена, бо a = b = √2 ірраціональні, а число a^b раціональне.
  * Якщо ж c ірраціональне, то побудуємо a = √2^√2, b = √2, тоді a^b = (√2^√2)^√2 = √2^2 = 2, знову раціональне.
**▲**

Ок, ми довели, що існують ірраціональні числа a, b, для яких a^b раціональне.
Але ми не знайшли жодної конкретної пари!
Є дві пари-кандидати: (√2, √2) та (√2^√2, √2), але яка пара насправді підходить, з самого доказу ми не знаємо.
В такому дусі можна запросто побудувати доказ, де вибір буде й з нескінченної кількості.
Тобто ніби-то існує, а ткнути пальцем, нікуди.

Пройшли роки, пристрасті уляглися.
Зараз це просто дві паралельні системи аксіом.
Інтуїціоністський доказ вартує трохи більше, бо більше обмежень.
Але всі результати корисні.
CIC та MLTT це приклади інтуїціоністських систем.
Відповідні мови програмування також.
Чи означає це, що їх не можна використовувати для класичних доказів?
Ні, зазвичай додати нову аксіому як два байти переслати.
Пишемо декларацію функції, маркуємо її як аксіому,
що на практиці означає прохання компілятору повірити на слово, що така функція є.

## Теорія і практика

Настав час зробити деякі підсумки.
Багато хто може подумати, що залежні типи це суто теоретична фігня, яка не має жодного відношення до практики.
Думаю це не так.
Більшість мов програмування зі залежними типами це Haskell-подібні мови, які дозволяють вирішувати більшість звичайних бізнес задач.
Так, трохи специфічно в деяких місцях.
Але для Lean 4 існує проміжна компіляція в сішний код, тому навіть по швидкодії вони якщо й програють, то не так драматично як той же Python.

А як же повнота по Т'юрінгу?
Ну... по-перше, для більшості практичних задач, як-то розібрати JSON, зробити SQL, тощо, повнота по Т'юрінгу не має нічого.
Структурної рекурсії для цього вистачає вище криші.
По-друге, всі мови зазвичай містять ключові слова, аналоги unsafe у C# та Rust, які знімають обмеження при написанні коду.
Ця функція не може бути доказом, але ніхто не забороняє її викликати.
Скажімо, умовний метод `run_web_server` не буде тотальним, бо ми не можемо гарантувати, що вона колись завершиться.
А от `handle_request` буде тотальний, тут ми гарантуємо, що обробка запита колись закінчиться.

Які є мови програмування зі залежними типами?

По-перше, це Lean 4, багато разів озвучували.
Дуже динамічно розвивається спільнотою математиків, які формалізують багато доказів.
Проте замах був на повноцінну практичну мову програмування, генеруємий код також досить швидкий.

Далі, це Rocq, який колись був відомий під ім'ям coq, яке замінили через асоціацію з чоловічими геніталіями.
Це динозавр, який початково розроблявся саме під потреби математиків, тому він майже не зручний для програмування.
Тому в парі з ним живе OCaml, теж Haskell-подібна мова за духом, тільки поза його екосистемою.
Це не випадковість: OCaml і Coq зростали пліч-о-пліч в одній лабораторії INRIA ще з 80-х, Coq навіть написаний на OCaml.
Це й досі працююча зв'язка: програми в OCaml, докази в Rocq.

Далі, Agda, це інший академічний проєкт, яка працює в Haskell оточенні.
Для її виконання треба рантайм GHC (RTS).
З плюсів це можливість легкої інтероперабельності з розвинутою екосистемою Haskell.
Але MLTT робить програмування досить специфічним, зазвичай проходиться програмувати через дірочки...
Виглядає так: спочатку пишеш в певному місці плейсхолдер `?`, що одначає тут має бути щось, не знаю що саме.
Потім можна подивитися деталі: який тип очікується, тоді можна його трохи уточнити, часто через інші плейсхолдери.

Останнім в списку буде Idris, це мова програмування яка створювалася не для математиків, а більше для програмістів.
В Idris 2 головна фіча це QTT, контроль за змінними.
В математиці числа визначаються концептуально як список одиничок: п'ять це `[1, 1, 1, 1, 1]`.
Так простіше писати докази, але в рантаймі швидкодія впаде так, що Python здаватиметься гепардом.
Для `Nat` компілятори це лікують самі, підміняючи на BigInt, але це спецкейз, а в залежних типах таких «існує лише заради доказу» речей повно.
В Idris є спосіб маркувати змінні: це тільки на етапі компіляції, що лише у runtime, а що й там й там, щоб запобігти цьому.

Якщо вас зацікавила ця тема, то гугліть Software Foundations, це потясні лекції по основам, дуже в захваті.
Це шлях rocq.

І, повертаючись до теми. Ізоморфізм Карі-Говарда це кінець 60-х. Як саме він формулювався, коли навіть підхожих мов програмування тоді не уснувало?
Секрет простий, мова йшла там про лямбда числення...
